# Cyclometer

Panasonic EZ（2025年型 電動アシスト自転車）のために作った、自作サイクルコンピュータです。

1970年代の子供用自転車に付いていたアナログ速度計の意匠を、Raspberry Pi Zero 2 WH と
3.5インチ液晶で再現しています。ホイールに取り付けた磁石をホールセンサーで検出し、
パルス間隔から速度・距離・加速度を求めます。

<p align="center">
  <img src="pict/cyclometer01.jpg" width="460" alt="ハンドルに装着したメーター">
</p>

GPS ベースのサイクルコンピュータと比べて、次の点で有利です。

- **更新頻度**：20 km/h で毎秒約11パルス。GPS ロガーの 0.25 Hz に対して桁違い
- **速度精度**：位置の差分ではなく回転を直接数えるので、数メートルの測位誤差が乗らない
- **応答性**：ノイズがほとんどないため強い平滑化が不要で、加減速に遅れずに追従する
- **場所を選ばない**：建物に囲まれた道、トンネル、屋内でも動作する

実測では、GPS が苦手とする低速・切り返しの多い区間で顕著に差が出ました。

|---|---|

## 配線

<p align="center">
  <img src="pict/cyclometer04-hall-sensor.jpg" width="380" alt="ホールセンサーの取り付け">
</p>

センサーは前輪のフォークに固定し、磁石はスポークがクロスする位置（半径約7cm）に
取り付けています。

| センサー | 接続先 |
|---|---|
| 茶（V+） | 5V（物理2番ピン） |
| 青（V−） | GND（物理39番ピンなど） |
| 黒（OUT） | GPIO16（物理36番ピン） |

NJK-5002C は電源に 5V を必要としますが、出力は NPN オープンコレクタなので、
**プルアップ先を 3.3V にすれば 3.3V の GPIO に直結できます。**
コード側で内部プルアップを有効にしているため、外付け抵抗は不要です。

3.5インチ液晶が物理1〜26番ピンを占有しているため、信号線と GND は
27番以降の空きピンを使っています。

## 使い方

```bash
sudo apt install python3-pygame python3-libgpiod
git clone https://github.com/kimux/cyclometer.git
cd cyclometer
```

**アナログメーター表示**

```bash
python3 gauge.py
```

**コンソールの数値モニタ**（磁石の調整・センサーの診断用）

```bash
python3 measure.py
```

**手元での確認**（GPIO 不要。Mac でも動きます）

```bash
python3 gauge.py --simulate --windowed --clock on
python3 measure.py --simulate
```

**文字盤のプレビュー**（速度:距離:ピーク を指定して1コマだけ描画）

```bash
python3 gauge.py --shot 27.3:12.345:36.4
```

走行ログはスクリプトと同じディレクトリに `ride-NNNN.csv` として連番で出力されます。
`--log-dir` で変更できます。

## 画面

- **速度**：0〜40 km/h。アシストが切れる 24 km/h を緑と橙の境目で示しています
- **オドメーター**：機械式ドラム風。最下位桁は 1m 単位で連続スクロールします
- **時計**：NTP 同期しているときのみ表示。Zero 2 W は RTC を持たないため、
  同期していない時刻は表示しません
- **ピーク**：針が到達した最高速度に赤丸が残ります
- **警告**：磁石の脱落を検出すると左下に表示します

## 設計上の注意点

### gpiod にデバウンスを設定してはいけない

`gpiod.LineSettings` に `debounce_period` を指定すると、**高速側でパルスを取りこぼします。**

BCM2835 はハードウェアデバウンスを持たないため、カーネルがソフトウェアで代替します。
その実装は割り込みの後に遅延ワークでピンを読み直す方式で、遅延は jiffies 単位に
丸められます（HZ=1000 なら最小 1ms）。さらにイベントのタイムスタンプが本来の
エッジ時刻ではなく再読み取りの時刻になります。

結果として、**1ms より短いパルスが丸ごと捨てられます。** 速度が上がるほど磁石の
通過時間は短くなるので、速度に比例して取りこぼしが悪化します。

実際にこれで、7 km/h で 71% のパルスを失っていました。ホールセンサーの出力は
シュミットトリガを通っておりチャタリングしないので、デバウンスは不要です。
ノイズ除去はソフトウェア側で、ありえない速度（90 km/h 相当）として弾いています。

### 周長は実測すること

20×1.75（ETRTO 47-406）に対して、一般的なサイクルコンピュータの周長表は
1515mm としていますが、これは外径 482mm 相当で、実寸と合いません。

```
外径 = 406 + 47×2 = 500 mm
周長 = π × 500 ≒ 1571 mm（無荷重）
```

GPS トラックの直線区間と照合した結果、実際には **約 1560mm** でした。
このリポジトリの既定値は 1560mm です。荷重や空気圧で変わるので、
ロールアウト法（乗車した状態でタイヤを1回転転がして距離を測る）での確認を勧めます。

### 速度は1回転ぶんの窓で求める

磁石を複数使うと、取り付け角度の誤差がそのまま速度の誤差になります。
実測では 122.8° / 113.8° / 123.4° と、理想の 120° から最大 6° ずれていました。

そこで **Nパルス前との時間差**（＝ちょうど1回転）から速度を求めています。
窓の幅が常に1回転ぶんなので、**どの磁石から数え始めても取り付け誤差が完全に
相殺されます。** それでいて更新はパルスごとに行われます。

### カルマンフィルタ

速度と加速度を状態とする等加速度モデルで、パルスの来ない間も推定を続けます。

パルスが与えるのは区間の**平均**速度であって瞬時値ではないため、観測を
**区間の中点時刻**に適用しています。等加速度なら平均速度は中点の瞬時速度に
等しいので、これで半区間ぶんの系統的な遅れが消えます。

実走データでの検証では、1回転窓の最高速 30.6 km/h に対しカルマン推定 30.7 km/h と
**ピークを削らず**、かつ定常時の両者の差は中央値 0.14 km/h でした。
移動平均による平滑化がピークを 22.8 km/h まで削るのとは対照的です。

## ファイル

| | |
|---|---|
| `measure.py` | 計測層。パルス入力、速度・距離・加速度の算出、CSV記録。単体でコンソールモニタとしても動作 |
| `gauge.py` | 表示層。`measure.py` を import してアナログメーターを描画 |

`measure.py` の `RideModel` はハードウェアに依存しないので、Mac 上で普通の
Python として過去ログを再生し、アルゴリズムを検証できます。

---

## ログ形式

| 列 | 内容 |
|---|---|
| `t_ns` | CLOCK_MONOTONIC のナノ秒。解析にはこちらを使う |
| `wall_iso` | 壁時計。`clock_synced` が 1 のときのみ信頼できる |
| `clock_synced` | NTP 同期済みなら 1 |
| `pulse_index` | 累積パルス数 |
| `interval_s` | 直前のパルスからの間隔 |
| `width_s` | パルス幅（磁石の通過時間）。取り付け品質の指標 |
| `speed_kmh` | 1回転窓による速度 |
| `speed_inst_kmh` | 直近1パルスによる速度 |
| `speed_kf_kmh` | カルマンフィルタによる速度 |
| `accel_mps2` | 加速度 |
| `distance_m` | 累積距離 |
